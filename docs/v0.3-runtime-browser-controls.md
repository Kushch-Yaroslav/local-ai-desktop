# Runtime, browser and controls — local implementation report

Branch: `feature/v0.3-runtime-browser-controls`, based on `feature/live-browser` at `14d8068`.
The pre-existing untracked `runtime/` directory was retained. Installed `/opt/local-ai-desktop`, packages, versions, tags and release artifacts were not changed. No merge or release was performed.

## Architecture and changes

### 1. Fast Cooperative Pause

The previous explicit Pause waited for the current provider turn, then offered up to three checkpoint tool turns plus synthesis. With high effort, both waits could be long. Explicit UI Pause now sets a separate atomic intent immediately. A bounded socket watcher shuts down only the current provider connection, including silent streams, partial HTTP/chunk reads and compaction requests. It never sets the task's Stop token. Already executing tools finish; later calls in the same batch receive durable “not executed” receipts. Read workers check intent before starting.

Rust writes an append-only `PauseCheckpoint` containing Task Memory, deliverables and the existing plan, alongside the existing work counters and tool observation journal. Resume restores this checkpoint even without an Electron-supplied memory snapshot. A cut-off generation is discarded; successful tool results are retained. An interrupted compaction summary never replaces its source evidence. Explicit Pause also releases a loop-detector wait without restarting work. Stop keeps priority.

Pause phases use ephemeral stream/UI state: Pause requested, Finishing current operation (with the active tool label), Saving checkpoint, Paused, Resuming. They do not generate chat messages per phase. Electron records the paused attempt as `interrupted`, with a paused timeline marker, and selects its logical task for the next message. It does not present the task as completed merely because no LLM pause summary was generated.

### 2. Browser permissions and lifecycle

The original session was scoped to one run and closed in the runtime bridge's `finally`. The approval broker already binds grants to run ID, sender, root, category and exact detail; its end/pause cleanup was not bypassed. No evidence established that a completed run's approval grant leaked into the next run. A new run still needs a new explicit browser authorization.

Retained sessions are keyed by window owner plus conversation, and checked against project root. Each new browser operation reacquires agent ownership synchronously and renews authorization. Explicit denials remain sticky within that run; repeating the same call does not reopen an approval or silently retry. Error results distinguish browser approval (`layer`, reason, origin, project root), closed/cancelled sessions, unavailable Chromium and ordinary operation failures. The bridge logs the run, chat, project identity and diagnostic result.

Changing project/web scope, changing security mode, revoking run approvals, deleting the chat, closing the preview or destroying the owning window releases the associated preview. Retention is bounded to eight sessions. Chat Only hides the stream; Close Browser disposes the session. Browser close listeners are not accumulated across reused runs.

### 3. Interactive Preview

The same Chromium Page supplies agent actions, live CDP frames and later user input. Ownership is explicit (idle/agent/user/closed/unavailable). The hub authenticates the sender and session; the session validates input and checks ownership again when queued input runs. Agent takeover rejects queued user input and releases held keys/buttons. Input queues are bounded.

The renderer forwards scaled pointer input, scrolling, text, printable Unicode, key down/up (including WASD), Back, Forward and Refresh. Blur/cancel releases held input. Continuous frames remain live after run completion.

All input uses the existing restricted context: exact approved origin, GET only, bounded requests/bytes, no inherited credentials, service workers or WebSocket access, no downloads or extra tabs. CSP also restricts frames, objects, form submission and base URLs. Redirects must pass the same origin gate. A rejected ordinary navigation can restore the last approved URL once; failed recovery cannot loop forever. Unsafe scheme navigation cannot gain an unrestricted page.

The model's eight-screenshot limit now returns `SCREENSHOT_LIMIT` without marking the live feed failed. Ordinary selector/action failures likewise do not destroy a healthy screencast.

### 4–5. Live reasoning and controls UX

A dedicated trusted Rust protocol request stores a pending Effort/Strategy configuration. The runtime consumes it at the next agent boundary, updating strategy guidance and the provider options without resetting transcript, plan or tool history. `reasoning_applied` is emitted after the provider request bytes have been submitted, not on control acknowledgment. An active stream is not restarted for a settings change.

Conversation updates are serialized so rapid effort/strategy selections compose from the latest accepted selection. Existing model capability mappings remain authoritative: for example, Qwen3.6 has no Effort selector. The renderer retains requested/applied distinctions and shows compact pending/live markers and notifications outside chat. Pending defaults that outlive an attempt are saved for the next run, without a false live-applied notification.

Mode, Thinking On/Off, Web and project changes are blocked while running; context/model changes require runtime loading and remain blocked while generating. Tooltip text explains each restriction. The normal context selector still requires the existing explicit load action.

### 6. Context validation

Runtime identity previously normalized context/KV arguments differently from the persisted measurement key: one path retained KV-offload switches while the other excluded them. Both now use `stableRuntimeArguments`. Ephemeral assessments loaded from disk are reset and reassessed rather than trusted across sessions.

Fresh comparable measurements display Confirmed; restored/missing-telemetry states display a neutral previous-measurement explanation; sustained memory drift or a changed model/runtime identity requires revalidation with a specific reason. Existing immediate activation checks, critical memory guards, per-KV comparison and drift stabilization remain in place. Common warnings appear once per KV column instead of under every context size.

### 7. Tool edit reliability

Investigation confirmed that mutating tools already run sequentially and use runtime-owned current file revisions; only independent reads are parallelized. A new regression verifies two dependent replacements in one batch against successive file contents. No orchestration race was reproduced for those edits.

Exact-match and stale-revision protections are retained. Deterministically invalid mutation calls now enter the existing duplicate-failure guard immediately. An identical call is not executed again without updated file evidence; a successful read clears relevant edit failure fingerprints. The existing structured errors retain recovery instructions. Corrected arguments remain available.

## Limits

- Resume continues the agent task from durable state; it does not restore unfinished tokens or a backend KV cache.
- A safely finishing tool, disk sync or backend connection setup can extend Pause latency. There is no forced interruption of an atomic file write.
- Browser network/request budgets stay bounded for the lifetime of the retained session. Closing/reopening requires fresh authorization; denial is never automatically retried.
- Context validation was tested through production IPC/SQLite with controlled hardware telemetry; a new exhaustive Max Context measurement on the real GPU was not performed here.
- Real Qwen checks use 32K context. They do not certify all model families, the maximum physical context, long-running memory soak behavior or every OS/keyboard IME.
- Vite retains its existing large-chunk build warning. An existing Rust `unused_mut` warning remains outside the changes.
- No new planning framework, TodoProvider, MTP, Vision, visual debugging, MCP or multi-agent functionality was added.

Changes are intended for local review and subsequent integration into v0.3.0. Release packaging, installation, main merge and publication remain separate steps.
