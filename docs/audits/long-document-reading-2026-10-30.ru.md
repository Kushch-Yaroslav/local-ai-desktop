## Причины

1. **Разрастание заметок и постоянное уменьшение chunks.** Artemis сохранила 1×24 000, 3×12 000, 35×6 000 и 59×3 000 символов. После `finish_reason=length` runtime уменьшает источник вдвое, но не возвращает размер обратно. Промпт требовал девять пересекающихся полей и до 650 слов при фиксированном output budget 2048. Это провоцирует переполнение у многословной модели, даже без reasoning. Уже существующий внутренний запрос отключал thinking локально; отключать его глобально не требовалось. В последних non-stream raw responses reasoning отсутствует. Основной расход нельзя приписывать только видимым рассуждениям.
2. **Пять запросов не сохранили заметок.** Временная привязка response к сохранению (менее секунды) однозначно сопоставляет остальные 98 запросов. Неподтверждённые запросы №3, 7, 43, 103, 105 заняли 546 584 мс (9:06.584). Первые три соответствуют уменьшениям chunks, последние два — повторным неудачам на offset 447000. Backend finish reason в старом non-stream журнале не записан; точную причину каждого из последних двух нельзя доказать отдельно. В коде `Chunk processing incomplete` возникает при length, пустом content или неожиданном tool call; JSON и schema имеют отдельные ошибки.
3. **Ошибка теряла результат на границе инструмента.** До ошибки успели сохраниться 98 заметок. Но исключение отбрасывало весь накопленный результат `read_document`: внешняя модель получала лишь текст ошибки, без заметок/полного состояния. БД заметки не потеряла; модель не получила пригодный полный результат. `context()` содержит cursor и только 500 символов последней заметки. Даже успешный `read_document` передавал первые 32 заметки, отбрасывая поздние из непосредственного результата.
4. **Ошибочная блокировка resume.** Общая таблица ошибок `WebChatService` после двух ошибок одинаковых аргументов возвращала `ARTIFACT_DUPLICATE` для любого инструмента, включая `read_document`. Его аргументы по контракту одинаковы при корректном продолжении! Отдельный фильтр read-only повторов тоже не учитывал изменение offset. Это дефект приложения, а не доказательство плохого tool calling модели.
5. **Финал разрешался без покрытия.** При отсутствии tool calls runtime сразу принимал любой финальный текст. Инструкция «не заявлять EOF» не была программной защитой. Artemis переключилась на `read_file`, заново получила [0,10000) и [10000,34000), после чего ошибочно считала, что знает только 34 тысячи символов. Оба диапазона уже находились внутри сохранённого покрытия: 34 000 повторно доставленных символов, без добавления покрытия.

7 внешних действий: два реально исполнявшихся `read_document` (109:22.989 и 2:11.052), два заблокированных `read_document` с `ARTIFACT_DUPLICATE`, три `read_file` (один ошибочный). Последние занимали 18–19 мс; время внутри `read_document` — преимущественно модельные запросы, а не дисковое чтение. После первой ошибки не появилось новых подтверждённых заметок. Финальный ответ появился ещё примерно через 9:58.

Точную долю «бесполезных» токенов определить нельзя. 149 708 из 156 429 (95,70%) относятся к внутренней обработке по разности с внешними segments, но не все они бесполезны. Пять rejected запросов не добавили подтверждённых сведений; их точные output tokens неизвестны. Непрерывное покрытие заканчивается в главе 18: полностью обработаны главы 1–17, частично 18; главы 19–22 не обработаны.

## Проверка фактов

Оригинал проверен непосредственно, а не по пересказу Artemis. Непрочитанный финал особенно показателен: Artemis утверждает, что Штырь становится верным помощником/защитником Доктора. В действительной главе 22 Доктор обсуждает с Бенито действие фикта, возвращение вещей Штырю, оружие без боеприпасов и сопровождение до «Ростка»; считает, что тот не нашёл свой Путь. Это несовместимо с уверенным финалом о нравственном перерождении и служении Доктору. Придуманы и собственные названия глав. Старый ответ Qwen содержит конкретные сюжетные детали (Мао, фикт, пульт), но его полная поутвержденческая проверка не выполнена: 100% offsets — доказательство обработки диапазонов, а не истинности каждой интерпретации.

## Жизненный цикл и изменения

`User → conversation-owned attachment → AttachmentService.fullText` проверяет владельца и hash оригинала/извлечённого текста; preview ограничен отдельно и не служит полным источником → `ChatReadonlyTools.read_document` берёт первый непрерывный подтверждённый offset → отдельный tool-free model request на chunk → проверка завершения/JSON/структуры → независимая запись `chat_document_notes` → обновление progress → результат инструмента → `WebChatService` → финальный ответ. Checkpoints/compaction существуют отдельно от заметок. Rust bridge вызывает те же инструменты, но финальная защита этого изменения относится к Chat (`WebChatService`), а не к произвольному Agent workflow.

Изменены:

- `src/main/services/chat-readonly-tools.ts`: ошибка возвращает явный частичный результат с сохранёнными заметками и offset; cancel по-прежнему пробрасывается, подтверждения сохраняются. Передаются все заметки, без cap 32, и обнаруженные главы с EOF-границами, статусом покрытия и observation IDs. Компактная схема без дублирующих полей, язык источника, ориентир 100–400 слов по длине, output budget 1536–4000 по размеру источника. Заголовки подаются chunk-модели из реального текста. Пустые заметки отклоняются. Предоставленные `quote` проверяются как точные подстроки текущего диапазона перед сохранением. Это проверка цитат, не семантическая проверка всех утверждений.
- `src/main/services/web-chat.ts`: ошибки чтения не превращаются в artifact errors; одинаковый `read_document` учитывает состояние progress. После неполного document pass приложение само показывает частичное покрытие/ошибку и заканчивает ход **до следующего запроса модели**, предотвращая reasoning recovery loop и неподтверждённый финал. Возобновление следующим запросом сохраняет cursor. Эта защита не применяется к обычным обсуждениям книг.
- `src/main/services/document-memory.ts`: progress исключает некорректные диапазоны; общий detector глав исключает TOC без прозы.
- `document-reading-recovery.test.ts`, `chat-readonly-tools.test.ts`, новый `long-document-coverage.test.ts`: регрессии ошибок, quotes, пустых заметок, покрытия, resume и блокировки финала.
- `package.json`: повторяемая команда `npm run test:long-document`; для включения оригинала в coverage-тест — `LAD_TEST_BOOK="/home/yaroslav/Загрузки/Stalker book.txt" npm run test:long-document`.
- `scripts/audit-long-document.py`: повторяемый read-only экспорт запросов CSV и метаданных JSON. Новая runtime-диагностика сохраняет только hash/ID, offsets, durations, tokens, finish reason и размер заметки; текст документа/заметок/reasoning в неё не пишется.

## Проверки и экономия

Прошли TypeScript main compilation, `npm run typecheck`, `npm run lint`, тесты `document-reading-recovery`, `long-document-coverage`, `chat-readonly-tools`, `web-chat`, `chat-context`, `chat-telemetry`, `persistent-attachments`, `attachment-pipeline`.

Новая регрессия обработала оригинал: 536 811 символов, 23 последовательных запроса controlled backend, без пропусков и повторов, ровно 22 повествовательные главы. На синтетическом документе 912 035 символов возвращены все 39 заметок, включая последние после старого лимита 32. Подтверждены: сохранение после Stop, восстановление новым scope, полный EOF, сохранение при malformed/empty/false quote, отсутствие повторной обработки завершённого документа. Тест финальной защиты подтверждает ровно один внешний запрос: после ошибки второй запрос с выдуманным финалом не вызывается.

Это **не измеренная экономия 103→23 на Artemis**: 23 — результат детерминированного backend. Для воспроизведения старого сбоя ранняя остановка устранила бы 7 последующих внешних генераций (6 385 токенов по старым segments), но оставила бы задачу незавершённой; это предотвращённые расходы после ошибки, а не доказанное ускорение успешного чтения. Реальное время/токены нового полного прохода и качество нового пересказа пока неизвестны. Старое чтение Qwen примерно в 7,6 раза быстрее по wall time, но с другим окном, числом chunks и объёмом заметок; вывод о сравнительном качестве моделей по одному запуску не обоснован.

## Ограничения и следующие проверки

Локальный `127.0.0.1:8081/health` (default backend) и дополнительно проверенный порт 8080 в доступном окружении не отвечают. Активный runtime не переключался, другая тяжёлая модель не запускалась. Для реальной приёмки нужен изолированный профиль с доступным backend: маленький документ, затем ограниченные главы, затем вся книга, с проверкой главы 22 по оригиналу и замером общего usage/time.

Защита гарантирует отсутствие LLM-финала после **начавшегося и незавершённого** `read_document` в текущем Chat ходе. Если модель вообще не вызвала этот инструмент или пользователь вручную читает через `read_file`, автоматического распознавания намерения полного чтения пока нет. После перезапуска диапазоны и заметки доступны, но активный transient guard создаётся при новом вызове `read_document`. Ошибка требует следующего сообщения для продолжения; не скрывается автоматическими бесконечными retries.

Сохранённая заметка — принятый результат модели, а не доказательство понимания. Цитата может быть верной при неверной интерпретации; quotes не обязательны для совместимости. Не проверяется, что финальная модель действительно использовала каждую заметку. Все заметки теперь доставляются, но очень длинная память может потребовать context compaction; нет отдельного проверенного иерархического синтеза всех глав. Детектор глав эвристический (порог прозы 160 символов), короткие/нестандартно оформленные главы требуют дальнейшей поддержки. Нельзя считать основной критерий достоверного полного LLM-пересказа уже выполненным.

Экспорт старых запросов для локального просмотра: `/tmp/long-document-audit/artemis/{requests.csv,metadata.json}` и `/tmp/long-document-audit/qwen/{requests.csv,metadata.json}`. В CSV неизвестные метрики оставлены пустыми; offsets сопоставлены с сохранениями по времени, а не выдуманы из текста reasoning. Hash итогового commit сообщается отдельно после фиксации (самоссылка на hash внутри того же commit невозможна).
