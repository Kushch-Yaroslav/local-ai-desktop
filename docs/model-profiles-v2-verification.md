## Configuration and data paths

`runtime-settings` normalizes persisted optional family/advanced/default fields without discarding legacy profiles. `gguf-profile` inspects cached, bounded GGUF metadata and template. Architecture has priority; Harmony and model/template clues provide fallback. Manual family selection changes classification, while controls still depend on the inspected template. Custom profiles use the real GGUF training context. Existing catalog profiles retain identity and placement; an inspected replacement template controls reasoning rather than inheriting another model's controls.

`ModelProfileEditor` holds the pending draft. Save validates ranges, MoE architecture and advertised backend flags, persists the profile and leaves the current process running. Profile defaults apply only when the conversation has no explicit model-specific selection. A model switch resets those selections. Agent Strategy belongs to Local AI Desktop and remains available independently of Thinking, tools or Vision.

`llama-runtime-policy` builds actual request fragments: Qwen `enable_thinking` where supported; Harmony `reasoning_effort=low|medium|high`, default Medium. Memory-only defaults preserve that Medium default. A generic variable in an unknown template does not establish valid effort values. For a custom GGUF, an unknown MTP+Vision combination is no longer hard-coded as incompatible: actual embedded MTP/CLI checks and post-launch multimodal confirmation remain mandatory. The existing OpenAI streaming adapter consumes backend-normalized `reasoning_content`, final content and tool-call deltas; no arbitrary output prefix is removed.

`backend-capabilities` probes the selected executable's real `--help`, caching by binary identity. `advanced-placement` constructs allowlisted, shell-quoted arguments. Unsupported flags, invalid counts, incompatible dense/MoE controls and malformed tensor rules fail before the healthy backend stops. This does not claim to predict every CUDA allocation or validate arbitrary regex matches against all model tensors before launch.

`runtime-profile-identity` separates startup changes from request-only settings and includes binary, every GGUF shard, projector, placement and context defaults. Name, tools, family override, Thinking and Effort do not produce a false backend reload. Saved startup changes require Apply before a new generation, rather than pretending the pending settings are active.

## One process controller and rollback

The existing `LlamaRuntimeController` and shell launcher serialize Load, Unload, model switch and forced Restart. The request file is parsed as allowlisted data. The launcher snapshots its successful generated profile environment, effective GPU setting and backend environment. A failed reload restores that snapshot even if the saved profile with the same ID has already changed. Active profile, pending profile, actual process arguments and previous-attempt diagnostics are separate.

Unload waits for the owned server to exit and clears active model state while retaining Electron, history, checkpoint and profile. It never searches for arbitrary llama-server processes to kill. PID start-time checks protect against PID reuse. IPC rejects lifecycle changes during an active run; the UI offers a safe Pause and waits for the runtime owner to release the checkpoint. Successful retries clear the current error; prior attempt information remains in session diagnostics and launcher logs. Deleting the active profile requires unloading it first.

The dialog shows active/target model, GPU layers and context/KV, plus detailed startup changes and observed argv. Technical placement reports distinguish model, KV and compute allocations by CPU/CUDA buffer. They are startup allocation observations, not peak VRAM or exact per-expert placement.

## Test evidence and limits

Text log exports trim trailing whitespace; recorded JSON messages and original user logs are unchanged. Machine-readable results are in [model-profiles-v2](test-results/model-profiles-v2/). Synthetic metadata and controlled-backend Electron tests are explicitly labelled and do not count as model inference. Real GPT-OSS artifacts retain earlier harness failures as well as their underlying events; completion patches are correlated to start events by tool ID. Read-only resumed runs need not emit an unchanged Task Memory update; explicit `task_memory view` proves the checkpoint instead.

Real safe GPT-OSS tool calling establishes a bounded read-only flow, not universal Agent reliability. `svgsvgsvg` was not reproduced; no speculative parser patch strips it. Other model families have metadata/request tests, not new real weight runs for every quantization. Tensor regex matching and automatic fit remain dependent on the backend and hardware. GPU memory sampling is periodic and cannot claim to capture every transient peak. 13/14 layers are not promoted to stable presets by unrelated tests.
