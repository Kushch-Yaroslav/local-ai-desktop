# P1: early effort changes — analysis and decision

Analyzed against llama.cpp `d1d3c3396aa13a5f239109a822666c4870490ad5` and P0 `f18a6b2`.

Effort is supplied to chat-template construction (`common/chat.cpp:944–946`), before token streaming. The active request has no supported effort mutation operation. `tools/server/server-context.cpp:4816–4825` exposes POST /props only behind an option, but its handler contains `// update any props here` and returns success without implementing updates. Calling that endpoint would falsely acknowledge a change. No public FFI is involved in this application.

P0 already provides the appropriate interruption primitive: `rust-agent/src/main.rs` records Pause immediately; `agent/loop_runtime.rs` cancels the provider request, discards its incomplete assistant/tool-call draft, retains completed tool observations and writes a `PauseCheckpoint` to the task transcript. Pending effort/strategy can take effect when the user explicitly resumes that task. This is task recovery, not continuation of the interrupted stream or preserved KV state. A tool already running must reach its safe completion boundary; it cannot be relabeled complete from partial generated arguments.

A separate “apply now and automatically resume” action would need a coordinated transaction spanning the frontend generation owner, terminal pause event, persisted interrupted run, logical-task selection and resumed request. It must resolve Stop/cancel, chat switching, window disposal, errors and approvals without accidentally starting a new run or resurrecting a stopped task. The existing P0 APIs expose these as separate user operations; they do not supply an atomic pause-and-resume transaction. MTP does not change this constraint.

Decision: keep P0 next-request application and explicit Pause → Resume. Do not interrupt merely because a selector changed; do not add a second abort mechanism, pretend that /props applies effort, or ship an unverified automatic resume action. The opt-in real Qwen regression can run with MTP enabled (`LOCAL_AI_TEST_MTP=1`) and exercises the existing pause/checkpoint, resume, Medium/Fast and reverse XHigh/Deep application. Its measured results are recorded in the P1 verification report. A future confirmed action requires its own lifecycle coordinator and race tests before release.
