# P1 — MTP: реализация и проверка

Дата: 17 октября 2026. Ветка: `feature/v0.3-mtp-controls`, база P0: `feature/v0.3-runtime-browser-controls` (`f18a6b2`). Версии приложения, main, tags, релизы, установленный .deb и файлы моделей не менялись. Исходный незакоммиченный `runtime/` сохранён.

## Техническое решение

Обязательный анализ выполнен до реализации: [заключение](v0.3-p1-mtp-analysis.md). Приложение использует внешний **llama-server 0.4.1-dev**, build 1, commit `d1d3c3396aa13a5f239109a822666c4870490ad5`, через существующий owned supervisor. React → preload/IPC → TypeScript controller → request file/SIGUSR1 → launcher. Rust Agent Runtime получает токены по HTTP/SSE; новых bindings/FFI нет. Изучены соответствующие локальные исходники llama.cpp, не API другой версии.

Capability проверяется независимо для GGUF и executable. Для `qwen35`/`qwen35moe` проверяются один nextn-слой, наличие trunk, размеры projection/norm тензоров и нахождение их известных quantized payload внутри файла (включая split GGUF). Одного имени или metadata-флага недостаточно. Backend должен объявлять `draft-mtp` в ограниченном `--help` probe. Реальное включение дополнительно подтверждается созданием MTP context, startup log и настоящими drafted/accepted counters. Проверка директорий не заменяет загрузку и выполнение модели.

Обе найденные Qwen имеют встроенные головы. Отдельный GGUF для них не нужен, загрузок из интернета нет. Qwen3.6-35B-A3B проверена структурно; реальные inference/benchmark выполнены на Qwen3.8-27B Q4_K_M (`qwen35`). Произвольные внешние MTP-файлы и обычные draft-model алгоритмы этой функцией не поддерживаются.

## Runtime и UI

- **Auto**: проверка совместимости, затем MTP либо обычный decoding. При неудачной инициализации Auto — одна попытка безопасного Off с сохранённой диагностикой; повторные poll UI не перезапускают модель. Этот путь отказа не испытывался реальным искусственным OOM.
- **On**: явная ошибка при отсутствии backend/весов; успешный Off не выдаётся за On.
- **Off**: явный `--spec-type none`, включая возврат после On. Консервативный MTP default: максимум два draft-токена.
- Выбор сохраняется отдельно для модели. Requested, applied mode и фактический speculative state разделены. Прежний бинарный переключатель из setup заменён компактным MTP control рядом с контекстом.
- Переключение загруженной модели требует явного подтверждения. Перезапускается только собственный llama-server: модель, target/MTP contexts и KV-cache пересоздаются. История, Rust checkpoint, задача и Browser session сохраняются. Активная генерация блокирует изменение в UI и IPC; автоматического Stop нет.
- Метрики принятия видны в tooltip как cumulative counters за жизнь текущего server; они отделены от обычного tokens/sec. Недоступные показатели не подменяются нулями.
- Профиль измерения контекста различает MTP и Off; read-only `--metrics` исключён из identity, чтобы счётчики сами не вызывали повторное предупреждение. Старые результаты не удаляются.

## Реальные замеры

RTX 3090, 24 GiB, driver 580.178.04; CUDA. Один GGUF, context 16384, target/draft KV Q8_0, GPU layers 999, parallel 1, flash-attention on, seed 42, temperature 0, cache_prompt=false. Без projector. Одинаковые prompts и sampling/лимиты во всех режимах: A/B — 1536, D — 4096 токенов. Все пять переключений и 20 сценариев завершились успешно. Первичные короткие лимиты 768/1536 потребовали калибровки: кодирование/reasoning не укладывались в них; они не включены в итоговые успешные замеры.

A — технический ответ, B — TypeScript retry с AbortSignal, C — реальный Rust agent с двумя последовательными read_file, D — reasoning и финальный ответ. Один набор сценариев на каждый режим, три повторения Off и два MTP (On/Auto), а не статистически строгий многократный benchmark. Значения ниже — конкретные измерения, не обещание ускорения.

Во всех режимах сохранены отдельные total GPU snapshots. Разница VRAM после прогрева около **762 MiB**; различие RSS нельзя целиком приписывать MTP, поскольку длина reasoning тоже изменилась.

MTP acceptance: A **61.9%**, B **90.8%**, C **95.6–97.3%**, D **81.1–81.3%**. C во всех пяти режимах выполнил два успешных чтения, завершил задачу, не дал повреждённых tool-call сообщений или ошибок. Для C единого tokens/sec и TTFT не собиралось; прочерки ниже означают отсутствие показателя.

Reasoning D: Off — **59.68 сек / 1733 токена**, On — **62.23 сек / 3409 токенов**, Auto — **62.59 сек / 3409 токенов**. Несмотря на большее tokens/sec, полный ответ с MTP здесь оказался медленнее. Все ответы завершили reasoning и вернули финальный текст; ограничения генерации в итоговом наборе не достигнуты.

Перезагрузка занимала 4.52–8.52 сек. После каждого переключения прежний PID отсутствовал; после cleanup отсутствовали все пять PID. Off после перезапуска supervisor восстановил сохранённую настройку и прежние память/скорость.

## Точность последовательности токенов

Короткий native greedy test с seed 42 дал одинаковые 64 token IDs. Отдельный более длинный тест с одним и тем же результатом /apply-template и фиксированными параметрами воспроизвёл **Off 699 → On 661 → Off 699**; первое отличие — индекс 61 (62-й токен). Повторный Off совпал полностью, prompt во всех трёх режимах одинаков. [Token comparison JSON](test-results/p1-mtp-token-comparison.json) сохраняет все IDs и тексты; воспроизведение: `LOCAL_AI_MTP_TOKEN_COMPARISON=1 npm run test:mtp:qwen`.

Это воспроизводимое различие backend, а не доказанная полная эквивалентность. Инспекция `server-context.cpp:3909–3917` подтвердила обычную проверку draft токенов target sampler (`common_sampler_sample_and_accept_n`); synthetic acceptance в команде не включалась. Причина различия logits/численных траекторий между одиночным decoding и MTP verification не локализована до конкретного kernel. Численные различия graph/batch/recurrent rollback — гипотеза, не установленная причина. Исправлений llama.cpp без доказательств не вносилось. Точное совпадение длинных greedy-последовательностей остаётся открытым ограничением.

## Experimental Interrupt & Resume

[Обязательное исследование](v0.3-p1-interrupt-analysis.md) выполнено. `/props` в этой версии не меняет effort; effort участвует в подготовке шаблона запроса. Оставлено безопасное применение на следующем обращении. Действие автоматического pause-and-resume не добавлено: для него ещё нужен согласованный lifecycle при Stop, смене чата, закрытии окна и approvals. Пользовательский Pause → Resume переиспользует P0 checkpoint и проверен на реальной Qwen с MTP. Продолжение незаконченного reasoning/KV-cache без потерь не обещается.

## Ограничения и готовность

Основной P1 реализован и готов к ревью: настоящий embedded MTP, Auto/On/Off, корректные состояния, подтверждённая перезагрузка, сохранение чата, реальные сравнительные метрики и регрессии. Это не опубликованный релиз. До широкого выпуска нужны дополнительные длительные agent/edit workloads и локализация причины длинного greedy-расхождения в backend.

Не сертифицированы Qwen3.6 inference (только веса/архитектура), внешние MTP GGUF, CPU/Vulkan/прочие GPU, предельные контексты с MTP, искусственные OOM/rollback на реальной модели и независимая реальная модель без MTP. Точный непрерывный пик RAM/VRAM не измерялся. Ускорение не гарантируется; Off остаётся безопасным способом отключения. Max-context сохранность проверена автоматическими IPC/профильными тестами; новый полный поиск максимума VRAM на реальной Qwen не выполнялся.

После работы P2/Browser Vision не начинался. Merge, release, tags и обновление установленного приложения не выполнялись. Исходный `runtime/` остаётся единственным незакоммиченным пользовательским каталогом; артефакты benchmark игнорируются, компактные результаты сохранены в этом отчёте.
