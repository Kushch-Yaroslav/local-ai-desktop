## Capabilities and boundaries

Chat exposes `list_attachments`, `attachment_metadata`, `read_file`,
`search_attachments`, `read_document`, `document_memory`, `save_chat_note`,
`list_observations`, and `read_observation`. Its `read_file` accepts only a
conversation attachment ID, never an arbitrary path. Ordinary web and structured
attachment data tools retain their existing controls. `read_browser` is available
only for an already-open, scoped Browser Workspace when web access is enabled.
It supports diagnostic `read` and bounded selector `inspect`.

Runtime tests reject edits, terminal, git, project mutations, extra path
arguments, cross-conversation attachment IDs, traversal, managed-source or
extracted-text symlink escapes, substituted extraction references, and changed
content hashes. Notes and imported copies are app-managed data; Chat tools
cannot edit user files. There is no unrestricted Chat filesystem access.

Real Chromium tests verify diagnostic reads preserve page identity, URL,
ownership and approval count. Clicks, navigation and script arguments are
rejected, unrelated conversations have no reader, and stale readers fail after
close. Existing static/loopback origin, approvals, pause/resume, live reload
and server recovery tests pass.

The shared attachment bridge was tested with real Rust orchestration and a
controlled SSE provider: text beyond the preview reaches the model through
`read_conversation_file`, and reopening SQLite and returning to Chat preserves
the same attachment ID. Agent planning schemas and the existing project read
contract remain distinct. This bridge test does not claim autonomous real-Qwen
Agent behavior or formal verification of a user project.

## Output accounting

Controlled HTTP/Electron/SQLite tests confirm a **50,000 aggregate completion
token budget** across three inference streams, one persisted assistant message,
no persisted synthetic continuation turns, boundary deduplication, natural EOS,
no-progress termination, context exhaustion, backend failure and User Stop.
Controlled usage counts establish application transport and persistence; they
are not a 50K real-model generation.

A real Qwen control deliberately forwarded `max_tokens=128` for its first two
requests. Actual backend finish reasons were **`length`, `length`, `stop`**;
the application continued only the first two and joined the three segments.
The proxy records both the application's requested cap and the smaller
forwarded test cap. A separate live stream was stopped by the user action and
its partial text persisted. Cancellation has no invented backend finish reason.

The historical user experiments were rechecked in the existing log:
**6,286** and **16,212** completion tokens, both **`finish_reason=stop`**, both
requested/effective `max_tokens=32768`, context 65,536. Neither proves a 16K
technical limit. Backend completion accounting includes reasoning/protocol;
visible text and reasoning tokenization are diagnosed separately.

The final ordinary-cap long-writing experiment generated **12,931 completion
tokens** (12,930 visible text tokens, zero reasoning text tokens), **55,775
characters**, in **one** request with requested/effective cap 32,768. The actual
backend finish reason was **`stop`**, with no automatic continuation. The
request asked for 24,000–28,000 tokens and 24 chapters; the model wrote only
9 numbered chapter headings and ended mid-phrase. It repeated **41 exact
paragraphs longer than 100 characters**. These are model repetitions within
one segment, not duplicates introduced at continuation boundaries.

Thus ordinary long-writing **transport/accounting passed, but requested length
and content quality did not**. Real-model 50K output remains **unconfirmed**.
A natural `stop` is respected even when incomplete prose suggests otherwise;
the host does not relabel EOS as a technical truncation or force unbounded
continuation. Structured long-writing generation remains future work. The
implementation does not promise exactly 50K visible text tokens or eliminate
repetition generated inside one model segment.
