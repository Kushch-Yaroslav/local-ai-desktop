# Экспериментальное ускорение моделей и память

Руководство описывает встроенный llama.cpp runtime v0.3.2.0. Набор доступных настроек зависит от GGUF и возможностей backend.

## Динамический кэш MoE-экспертов

MoE-маршрутизация выбирает экспертов для каждого токена. При поддержке llama.cpp хранит веса экспертов в RAM и помещает востребованных экспертов в GPU-кэш. Он отделён от обычных GPU-слоёв и KV state. Режимы: «Стандартный» без кэша, «Автоматический» с ограниченной оценкой для распознанных комбинаций модели/backend и «Ручной» с вариантами 2, 4, 8, 12 или 16 GiB, если их допускает текущая оценка VRAM.

Проверенная модель — Qwen3-Coder-Next 80B Q4_K_M (qwen3next, 48 блоков, 512 экспертов) на встроенной CUDA-сборке. Это не универсальная совместимость с MoE. Больший кэш может ускорить генерацию, не повлиять или замедлить её. CPU- и GPU-ядра могут выдавать разные logits и ответы; побайтовая идентичность не гарантируется.

Исторический парный тест на RTX 3090 использовал экспериментальный backend и allocation контекста 4K:

| GPU-кэш экспертов | Медиана decode |
| --- | ---: |
| 0 GiB | 29,07 tok/s |
| 8 GiB | 36,96 tok/s |
| 12 GiB | 46,82 tok/s |
| 16 GiB | 56,25 tok/s |

Результат 16 GiB был примерно на 93,5% быстрее в том тесте. Это не гарантия для иных запросов, контекста, backend, моделей или компьютеров. Позднее встроенный runtime загрузил Qwen с кэшем 16 GiB и 64K Q8 GPU KV и завершил короткий ответ. Benchmark с заполненным контекстом 64K не проводился.

## Расширенное размещение слоёв

Метаданные GGUF задают число блоков и имена тензоров. Сетка и диапазоны выбирают обычные тензоры блоков для GPU, например `3-12, 15, 16-20`. Блоки не являются гарантированными «слоями программирования» или «рассуждений». Размещение использует tensor overrides и поддерживаемые buffer types llama.cpp; неполные метаданные, архитектура или backend ограничивают выбор. CPU MoE настраивается отдельно, поэтому экспертные тензоры могут оставаться в RAM независимо от обычных слоёв.

## Память и контекст

Оценка GPU учитывает известные веса, кэш экспертов, attention KV, гибридное recurrent state, запас для вычислений и резерв. Фактические allocations подтверждают runtime-логи. Q8 KV требует меньше памяти, чем FP16, но точность KV задаётся отдельно.

При явном mmap и ограниченном no-repack размещении страницы GGUF являются вытесняемыми file-backed mappings, а не обязательной anonymous памятью. Обращение к странице требует физической RAM; её вытеснение замедляет работу. Оценка RAM разделяет обязательные allocations, запас runtime и резерв ОС, проверяет cgroup `MemoryMax`. Launcher сохраняет `MemorySwapMax=0`, контроль RAM/PSI, VRAM preflight и резерв памяти. Общесистемный swap-out только записывается в диагностику и сам по себе не останавливает модель.

Allocation 64K не означает обработку 64K токенов. Qwen использует гибридные attention/recurrent механизмы, поэтому её память нельзя описать одной общей формулой KV.

## Известные ограничения

- Experimental Alpha, не стабильный продукт.
- Ускорение MoE проверено на узком наборе моделей и оборудования.
- Побайтовое совпадение ответов CPU/GPU не гарантировано.
- Произвольное размещение слоёв ограничено именами тензоров, архитектурой и buffer types backend.
- Длинные Agent workflow и все комбинации инструментов проверены не полностью.
- Возможны семантические циклы и избыточное исследование файлов.
- Review может задерживать показ финального ответа Agent до конца генерации.
- mmap working set под давлением памяти может вытесняться и снижать скорость.
- Некоторые старые regression сценарии остаются не пройдены; подробности в release notes.
- Benchmark с заполненным контекстом 64K не проводился.
- Runtime и упаковка проверялись на Linux x86_64, преимущественно Ubuntu 24.04 и испытанной конфигурации NVIDIA/CUDA. Универсальная поддержка других GPU, драйверов, дистрибутивов и ОС не заявляется.
