# Scenario-aware Browser QA и адаптивность

[English](../en/BROWSER_QA.md) · [Руководство](USER_GUIDE.md)

Browser QA использует текущий Native Browser / Playwright / CDP и Verification Gate. Агент выбирает проверки по заданию и acceptance criteria. Выполненный план означает выполненные действия; Verified означает доказанное конкретное требование.

## Когда нужна мобильная проверка

В контекст планирования без дополнительной LLM передаётся объяснимая рекомендация. Она учитывает запрос, критерии, текущий план, изменённые UI-файлы, фактические участки правок и прежние viewport findings. Явное требование мобильной версии требует соответствующих сценариев. Создание лендинга, изменение layout, JSX-навигации, форм или модальных окон обычно делает проверку релевантной.

Backend API, миграции, Rust Agent Runtime, серверный рефакторинг и исправления типов обычно обходятся без responsive QA. Само расширение `.css` недостаточно: изменение переменной цвета не требует пяти размеров. Изменение JSX может потребовать проверку без правок CSS. Рекомендация доступна агенту в текущем planning-контексте; агент уточняет решение по смыслу задачи. Это не безусловный completion gate.

Связанные UI-правки группируются до осмысленного checkpoint. Пропуск нерелевантной проверки не создаёт незавершённого QA-плана. Постоянной настройки «всегда тестировать мобильную версию» нет.

## Viewport и изоляция

| Профиль | Размер |
| --- | --- |
| `small-mobile` | 320 × 640 |
| `mobile` | 390 × 844 |
| `large-mobile` | 430 × 932 |
| `tablet` | 768 × 1024 |
| `desktop` | 1440 × 900 |

По умолчанию диагностический responsive checkpoint использует mobile + desktop. Можно выбрать 1–5 размеров или `{width,height}`: ширина 280–1920, высота 320–1600. Полный набор не обязателен.

Проверка выполняется во временной изолированной Page существующего Chromium. В Electron это скрытая Native Page через ту же защищённую фабрику, без нового Electron-окна; в CLI — временный context того же браузера. Исходная страница сохраняет размеры, URL, формы, scroll и ownership. Временные ресурсы закрываются в `finally`, при Stop и Pause. User input не направляется на QA Page.

QA начинает с чистого состояния; пользовательские cookies/storage и незавершённые формы не копируются. Необходимые состояния задаются preconditions и безопасными steps. При HTTP 401/403 возвращается Auth Required. Обход авторизации не выполняется. Сохраняются ограничения origin, GET, popup, WebSocket, файлов и разрешений. Реальные платежи, отправка сообщений и другие необратимые действия не входят в автоматические проверки.

## Что устанавливает DOM

- Размер документа и viewport сопоставляется с геометрией реально видимых элементов. Горизонтальная карусель внутри собственного scroll container не считается переполнением документа.
- Проверяется горизонтальная доступность важных интерактивных областей. Скрытые responsive-варианты и элементы внутри намеренно прокручиваемых/обрезаемых контейнеров исключаются.
- Перекрытия по hit testing, обрезанный текст без ellipsis, слишком крупные изображения и выходящие за экран диалоги дают кандидатов. Пересечение прямоугольников само по себе не доказывает баг.
- Только определённые геометрические нарушения дают Failed. Неоднозначные кандидаты или достижение лимита инспекции дают Inconclusive / Not Verified.

Ограничения инспекции: до 2000 DOM-элементов, 60 интерактивных областей для hit testing и 40 findings. Данные сохраняются в scenario evidence. Проверка `layout equals 0` доказывает только отсутствие обнаруженных нарушений DOM-границ данного viewport и маршрута. Она не доказывает визуальную корректность Canvas/WebGL или всего сайта.

## Vision и функциональность

В `responsive.vision=auto` имеющийся Browser Vision вызывается для Canvas или неоднозначных DOM-кандидатов. `off` оставляет DOM QA; `on` запрашивает визуальный анализ выбранных размеров. Отсутствие мультимодальной модели не отключает функциональные проверки. Скриншот и DOM findings передаются вместе; оценка Vision остаётся вероятностной и сама по себе не превращает кандидат в подтверждённый баг.

Мобильное меню, dropdown, вкладки, модальные окна и безопасные формы используют существующие `steps` и конкретные assertions. Отдельного click/type-движка нет. Скриншоты ограничены 2 MiB и масштабируются при необходимости до 1280 × 900 с сохранением исходного viewport в metadata; до 8 снимков и 12 MiB за QA operation.

## Сценарии и Verification Gate

Каждое требование связывается так: deliverable → immutable acceptance criterion → конкретный scenario с viewport/route → наблюдения и evidence → результат. Для разных обязательных размеров и маршрутов нужны отдельные критерии. `scenario_refs` выполняет зарегистрированную спецификацию без ослабления проверки. Desktop evidence, browser open и общий успешный load не подтверждают mobile criterion.

Пример создания адаптивного лендинга:

1. Агент реализует связанные секции и навигацию до checkpoint.
2. Регистрирует критерий `mobile-bounds` (kind `runtime`) с такой спецификацией и отдельный `desktop-bounds` с viewport `desktop`:

```json
{
  "target": "/index.html",
  "viewport": "mobile",
  "preconditions": [],
  "required_state": [],
  "steps": [],
  "assertion": {"source": "layout", "operator": "equals", "expected": 0},
  "timeout_ms": 6000
}
```

3. Для мобильного меню регистрирует отдельный kind `interaction`: precondition — кнопка меню видима; step — click на неё; assertion — меню стало видимым. Селекторы берутся из созданного приложения.
4. Выполняет `web_project` action `qa` с `scenario_refs`, исправляет подтверждённые дефекты и повторяет затронутые сценарии.

Для предварительной диагностики без подтверждения произвольных deliverables можно вызвать:

```json
{"action":"qa","path":"index.html","responsive":{"reason":"Готов checkpoint адаптивного лендинга","viewports":["mobile","desktop"],"vision":"auto"}}
```

Общие `viewports` не применяются к bound-сценариям: размеры фиксируются в каждом acceptance criterion. В панели QA показаны размеры, количество проверок, findings, функциональный результат и отдельный статус Vision. Технические наблюдения и идентификаторы доступны в details; Compact/Expanded и RU/EN сохраняются.

## Breakpoint, свежесть и лимиты

Для уже найденного дефекта можно запросить диагностический `responsive.breakpoint={minWidth:320,maxWidth:430,attempts:4}`. Сначала проверяются границы, затем середина соседней пары с разными результатами. Всего 2–5 попыток, остановка при диапазоне ≤16 px, отсутствии контраста или неоднозначном результате. Это наблюдаемый pass/fail диапазон, а не угаданный CSS breakpoint. Пробы не меняют и не подтверждают acceptance criteria.

Каждый сценарий хранит ревизии загруженных исходников. Повтор неизменённого responsive checkpoint переиспользует evidence и не создаёт новую verification record. Правка независимой статической страницы не обесценивает проверку другого маршрута; изменение загруженной зависимости требует новой проверки. Для dev server без прямого source mapping responsive-кеш отключён и применяется более консервативная ревизия проекта. Внешние runtime-изменения, не наблюдаемые браузером/сценарием, не гарантированно обнаруживаются кешем: задавайте явные state-preconditions и сценарии.

Общий QA anti-loop остаётся активен. Изменение описания, имени сценария или перезапуск страницы не создаёт новый прогресс. Лимиты отдельной операции сохраняются: 6 сценариев, 5 viewport, до 8 steps в сценарии, timeout 500–15000 ms, общий deadline runner 30 s и внешний envelope 90 s. Это не lifetime-бюджет полезных проверок.

Эмуляция размеров desktop Chromium не подтверждает работу iOS Safari, Android Chrome, touch, виртуальной клавиатуры или реального мобильного GPU. Изолированная Page не воспроизводит приватную пользовательскую сессию. Подтверждение качества ограничено конкретными проверенными assertions, маршрутом, размерами и ревизиями.

## Visual Layout QA: покрытие viewport, швы и resize

Visual Layout QA расширяет существующие Scenario QA, изолированную QA Page, сохранение снимков, source revisions и Verification Gate. Второй браузерный runtime или QA-движок не создаётся. Отсутствие DOM-overflow не доказывает визуальную непрерывность полноэкранной сцены.

Проверка уместна на осмысленном checkpoint, когда запрос, acceptance criteria и реальные UI-правки относятся к Canvas/WebGL, полноэкранному фону, высоте контейнера, обрезанному содержимому или конкретному визуальному дефекту. Предыдущие viewport/visual findings — дополнительная причина исследовать проблему. Backend API, миграции БД и внутренние Rust-правки не требуют этой проверки. Существующая контекстная QA-подсказка объясняет рекомендацию; решение принимает агент без отдельного LLM-классификатора. Запуск после каждой мелкой правки не нужен.

Assertion `source:visual_layout`, `operator:equals`, `expected:0` поддерживает:

- `path:coverage` + `selector`: проверяет покрытие CSS viewport границами **явно требуемого полноэкранного элемента**, с допуском 2 px. Незакрытая полоса — Failed конкретного требования. Это не доказательство, что каждый пиксель внутри Canvas нарисован правильно.
- `path:backing` + Canvas selector: сопоставляет backing store с CSS-размером × фактический DPR. Несовпадение — Suspected: низкое разрешение рендера может быть намеренным. Совпадение подтверждает только это измеряемое соотношение.
- `path:seams`: ищет устойчивые протяжённые горизонтальные/вертикальные контрастные границы в двух кадрах. Шов остаётся Suspected, включая намеренные разделители секций. Отсутствие кандидатов также не доказывает эстетическую корректность или отсутствие любых швов.

PNG RGB/RGBA декодируется с ограничением размера. Диагностика сравнивает цвета по обе стороны границы (средний контраст ≥24/255 на ≥80% выборки поперечного сечения), проверяет сохранение границы в двух кадрах, сохраняет укрупнённые RGB-признаки 8×8 и сопоставляет границу с bounds целевого элемента. Evidence содержит CSS-координаты, контраст, протяжённость, эвристическую уверенность, capture IDs, размеры изображения, DPR, scroll, хеши исходников и DOM-проверку каждого размера. Эвристическая уверенность не является вероятностью Vision. DOM, пиксельные кандидаты, функциональные проверки и мнение Vision отображаются отдельно. Header, градиент или декоративная линия не становятся ошибкой автоматически.

Пример условной полноэкранной сцены с нижней полосой 80 px и тёмно-фиолетовым переходом:

```json
{
  "action":"qa",
  "scenarios":[{
    "id":"scene-coverage",
    "goal":"Полноэкранная сцена покрывает viewport; исследовать нижнюю полосу и переход фона",
    "target":"/index.html#scene", "viewport":"desktop",
    "preconditions":[], "required_state":[], "steps":[],
    "assertion":{"source":"visual_layout","path":"coverage","selector":"canvas","operator":"equals","expected":0},
    "visual_layout":{"dpr":1,"resize":[{"width":1440,"height":700},{"width":390,"height":844}],"vision":"auto","state_key":"scene-ready"},
    "timeout_ms":14000
  }]
}
```

Укажите реальные preconditions/actions для нужного состояния приложения. Для acceptance evidence зарегистрируйте `kind:visual` с этой неизменяемой спецификацией, затем выполняйте `scenario_refs`. Диагностический сценарий без привязки не подтверждает произвольные deliverables. Разные маршруты/viewport и функциональные свойства требуют своих criteria. Детерминированный Verified возможен для конкретного измерения coverage/backing; швы и общие Vision-описания остаются ограниченными доказательствами. Desktop-снимок не подтверждает мобильную версию или движение объектов.

### До/после и динамические сцены

До исправления выполните диагностический сценарий и сохраните ID отчёта/сценария. После правки повторите его, добавив `visual_layout.baseline:{report_id:"<сохранённый UUID>",scenario_id:"scene-coverage"}`. Для acceptance-проверки точную baseline-ссылку зарегистрируйте в неизменяемом criterion до выполнения проверки. Baseline читается только из существующего приватного каталога captures, с ограничением размера и проверкой принадлежности проекту; исторический результат не становится свежим доказательством.

Должны совпадать маршрут, начальный viewport, DPR, последовательность resize, assertion, preconditions/actions, объявленный `state_key`, scroll/размеры снимка и хеш ограниченного состояния форм/dialog/details. Отчёт показывает исчезнувшие, сохранившиеся и новые регионы-кандидаты, а также изменение укрупнённых цветовых признаков. Несовпадающий или отсутствующий baseline блокирует сравнение. Изменение metadata не обновляет свежесть и не создаёт совпадение условий. Скрытое состояние, например камера игры, не гарантируется одинаковым: задавайте явные наблюдаемые preconditions. Восстановление приватной пользовательской сессии не подразумевается.

На каждом размере снимаются два кадра с интервалом 180 ms после ожидания 180 ms. Анимация не замораживается внедрением кода; пользовательский проект не меняется. Движущиеся частицы не проверяются pixel-perfect diff. Укрупнённые отличия — наблюдения, а не автоматические регрессии. Новая граница остаётся Suspected даже при подтверждении конкретного исправления покрытия. Длинные анимационные циклы и тонкие/диагональные дефекты могут быть пропущены.

### Целевой Vision, изоляция и лимиты

При доступном совместимом backend `vision:auto` вызывает один реальный анализ при наличии кандидатов; `on` требует целевого анализа, `off` сохраняет DOM/пиксельную диагностику. Существующий provider получает настоящий снимок, соответствующий baseline при совпадении условий, маршрут, CSS viewport, фактическое разрешение изображения, DPR, подозрительные области, bounds/backing/background и требование сценария. Вопрос явно направляет внимание на нижние 20% и найденные границы. Искусственного увеличения детализации нет. Без Vision детерминированные проверки продолжают работать. Fixture-ответы в тестах проверяют маршрутизацию, а не качество модели. Фраза «всё хорошо» не отменяет измеренное нарушение покрытия и не подтверждает произвольный visual criterion.

Один visual-сценарий на checkpoint, не более двух resize-переходов и шести кадров анализа. Действуют существующие лимиты: 8 captures, 12 MiB возвращаемых изображений, ≤2 MiB на снимок, изображение ≤1280×900. При этом рендерится настоящий независимый CSS viewport: готовый профиль или размер 280–1920 × 320–1600; снимок может быть уменьшен. DPR 1/2 эмулируется отдельно от CSS/backing/image pixels. Фиксированные CDP-команды обращаются только к принадлежащей приложению Native Page; browser-wide доступ остаётся запрещён. Stop/Pause/error закрывает временную страницу/контекст и освобождает ввод, не изменяя видимую пользовательскую страницу. Source freshness, повторное использование неизменённых результатов и anti-loop сохранены. Это desktop Chromium, а не проверка физического смартфона или автоматическая оценка эстетики.

В существующей RU/EN QA-панели отображаются Visual Layout QA, маршрут/viewport, подозрения и нарушения, координаты областей, сравнение до/после, отдельный Vision и причины блокировки. В деталях доступны измерения/captures и технические IDs. Адресные реальные browser-регрессии: `npm run test:visual-layout-qa`.

## Разрешения preview и последовательные задания в чате

**Один раз** разрешает текущий вызов browser tool и его ограниченные запросы к странице. Следующая отдельная операция требует нового согласия, если нет session grant. Внутренние изолированные страницы Responsive/Visual QA используют уже разрешённый origin и не запрашивают согласие на каждый viewport.

**В этой сессии** означает текущий чат в данном окне Electron, включая следующие Agent Runs, Pause/Resume и передачу браузера пользователю. Grant связывает категорию `browser_preview`, зарегистрированный проект, root, точный origin, security context и чат/окно. Для команд сохраняется привязка к конкретной команде и папке: разрешение preview не разрешает запуск shell. Grant отзывается явно, при реальной смене scope/режима или закрытии приложения/окна. Его можно увидеть и отозвать в Agent Security между заданиями. Повторное сохранение неизменённого каталога или режима не отзывает разрешения и не закрывает браузер.

**Абсолютный автопилот** автоматически разрешает read-only preview текущего зарегистрированного проекта: виртуальный `project-preview.invalid` либо поддерживаемый HTTP `localhost`/`127.0.0.1` с явным портом. Это не глобальное разрешение localhost: сессия сохраняет project/origin lock, а dispatcher отклоняет другой проект. Проверки методов GET, разрешённых файлов, symlinks, внешней сети, redirects, WebSocket, cookies/auth и лимитов не отключаются. Loopback-прокси соединяется непосредственно с 127.0.0.1 без DNS/proxy inheritance. Событие автоматического разрешения записывается в application log. Запуск сервера остаётся отдельной командой под обычной политикой выполнения; опасные команды не получают разрешение browser preview.

После завершения run живая Page остаётся у пользователя. Следующий run получает актуальный observer и новые cancellation/QA options и запрашивает управление перед разрешённой операцией. Истёкший сигнал предыдущего run не используется повторно. При наличии chat grant новый диалог не появляется. В панели различаются управление агентом/пользователем, пауза, закрытие, восстановление и блокировка политикой.

`open(path:"index.html#scene")` использует уже утверждённый origin сохранённой Page, включая localhost. Для новой сессии без origin используется виртуальный preview. Явный URL другого origin отклоняется и не повреждает рабочую Page. Чтобы перейти на другой origin, закройте preview и откройте его в новой разрешённой задаче; один проект не делает произвольные origin взаимозаменяемыми.

После технической потери Page/CDP явный `open` допускает одно пересоздание на run через существующую Native-фабрику. Старые callbacks/ресурсы остаются у старой Page. Явное пользовательское закрытие не вызывает скрытого восстановления в том же run; новая пользовательская задача может открыть страницу заново. Stop не перезапускает браузер; новая задача/Resume использует новые сигналы. Pause сохраняет существующие checkpoint/history штатным runtime.

Недоступный preview server и `ERR_FAILED` не равны user-close. Watchers прекращаются при закрытии Page/transport; ошибка финального refresh больше не уничтожает живую сессию. После восстановления сервера явно откройте утверждённый URL. Идентичные ошибки без изменения состояния по-прежнему блокируются anti-loop; подтверждённое пересоздание Page освобождает только browser-failure записи того же project slot. QA evidence/anti-loop не сбрасываются простым reopen.

Адресная проверка: `npm run test:browser-session`. Native/Rust E2E использует scripted provider и не является настоящим Qwen/Vision inference.
