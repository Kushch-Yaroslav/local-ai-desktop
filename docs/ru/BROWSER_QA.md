# Scenario-aware Browser QA и адаптивность

[English](../en/BROWSER_QA.md) · [Руководство](USER_GUIDE.md)

Browser QA использует текущий Native Browser / Playwright / CDP и Verification Gate. Агент выбирает проверки по заданию и acceptance criteria. Выполненный план означает выполненные действия; Verified означает доказанное конкретное требование.

## Когда нужна мобильная проверка

В контекст планирования без дополнительной LLM передаётся объяснимая рекомендация. Она учитывает запрос, критерии, текущий план, изменённые UI-файлы, фактические участки правок и прежние viewport findings. Явное требование мобильной версии требует соответствующих сценариев. Создание лендинга, изменение layout, JSX-навигации, форм или модальных окон обычно делает проверку релевантной.

Backend API, миграции, Rust Agent Runtime, серверный рефакторинг и исправления типов обычно обходятся без responsive QA. Само расширение `.css` недостаточно: изменение переменной цвета не требует пяти размеров. Изменение JSX может потребовать проверку без правок CSS. Рекомендация доступна агенту в текущем planning-контексте; агент уточняет решение по смыслу задачи. Это не безусловный completion gate.

Связанные UI-правки группируются до осмысленного checkpoint. Пропуск нерелевантной проверки не создаёт незавершённого QA-плана. Постоянной настройки «всегда тестировать мобильную версию» нет.

## Viewport и изоляция

| Профиль | Размер |
| --- | --- |
| `small-mobile` | 320 × 640 |
| `mobile` | 390 × 844 |
| `large-mobile` | 430 × 932 |
| `tablet` | 768 × 1024 |
| `desktop` | 1440 × 900 |

По умолчанию диагностический responsive checkpoint использует mobile + desktop. Можно выбрать 1–5 размеров или `{width,height}`: ширина 280–1920, высота 320–1600. Полный набор не обязателен.

Проверка выполняется во временной изолированной Page существующего Chromium. В Electron это скрытая Native Page через ту же защищённую фабрику, без нового Electron-окна; в CLI — временный context того же браузера. Исходная страница сохраняет размеры, URL, формы, scroll и ownership. Временные ресурсы закрываются в `finally`, при Stop и Pause. User input не направляется на QA Page.

QA начинает с чистого состояния; пользовательские cookies/storage и незавершённые формы не копируются. Необходимые состояния задаются preconditions и безопасными steps. При HTTP 401/403 возвращается Auth Required. Обход авторизации не выполняется. Сохраняются ограничения origin, GET, popup, WebSocket, файлов и разрешений. Реальные платежи, отправка сообщений и другие необратимые действия не входят в автоматические проверки.

## Что устанавливает DOM

- Размер документа и viewport сопоставляется с геометрией реально видимых элементов. Горизонтальная карусель внутри собственного scroll container не считается переполнением документа.
- Проверяется горизонтальная доступность важных интерактивных областей. Скрытые responsive-варианты и элементы внутри намеренно прокручиваемых/обрезаемых контейнеров исключаются.
- Перекрытия по hit testing, обрезанный текст без ellipsis, слишком крупные изображения и выходящие за экран диалоги дают кандидатов. Пересечение прямоугольников само по себе не доказывает баг.
- Только определённые геометрические нарушения дают Failed. Неоднозначные кандидаты или достижение лимита инспекции дают Inconclusive / Not Verified.

Ограничения инспекции: до 2000 DOM-элементов, 60 интерактивных областей для hit testing и 40 findings. Данные сохраняются в scenario evidence. Проверка `layout equals 0` доказывает только отсутствие обнаруженных нарушений DOM-границ данного viewport и маршрута. Она не доказывает визуальную корректность Canvas/WebGL или всего сайта.

## Vision и функциональность

В `responsive.vision=auto` имеющийся Browser Vision вызывается для Canvas или неоднозначных DOM-кандидатов. `off` оставляет DOM QA; `on` запрашивает визуальный анализ выбранных размеров. Отсутствие мультимодальной модели не отключает функциональные проверки. Скриншот и DOM findings передаются вместе; оценка Vision остаётся вероятностной и сама по себе не превращает кандидат в подтверждённый баг.

Мобильное меню, dropdown, вкладки, модальные окна и безопасные формы используют существующие `steps` и конкретные assertions. Отдельного click/type-движка нет. Скриншоты ограничены 2 MiB и масштабируются при необходимости до 1280 × 900 с сохранением исходного viewport в metadata; до 8 снимков и 12 MiB за QA operation.

## Сценарии и Verification Gate

Каждое требование связывается так: deliverable → immutable acceptance criterion → конкретный scenario с viewport/route → наблюдения и evidence → результат. Для разных обязательных размеров и маршрутов нужны отдельные критерии. `scenario_refs` выполняет зарегистрированную спецификацию без ослабления проверки. Desktop evidence, browser open и общий успешный load не подтверждают mobile criterion.

Пример создания адаптивного лендинга:

1. Агент реализует связанные секции и навигацию до checkpoint.
2. Регистрирует критерий `mobile-bounds` (kind `runtime`) с такой спецификацией и отдельный `desktop-bounds` с viewport `desktop`:

```json
{
  "target": "/index.html",
  "viewport": "mobile",
  "preconditions": [],
  "required_state": [],
  "steps": [],
  "assertion": {"source": "layout", "operator": "equals", "expected": 0},
  "timeout_ms": 6000
}
```

3. Для мобильного меню регистрирует отдельный kind `interaction`: precondition — кнопка меню видима; step — click на неё; assertion — меню стало видимым. Селекторы берутся из созданного приложения.
4. Выполняет `web_project` action `qa` с `scenario_refs`, исправляет подтверждённые дефекты и повторяет затронутые сценарии.

Для предварительной диагностики без подтверждения произвольных deliverables можно вызвать:

```json
{"action":"qa","path":"index.html","responsive":{"reason":"Готов checkpoint адаптивного лендинга","viewports":["mobile","desktop"],"vision":"auto"}}
```

Общие `viewports` не применяются к bound-сценариям: размеры фиксируются в каждом acceptance criterion. В панели QA показаны размеры, количество проверок, findings, функциональный результат и отдельный статус Vision. Технические наблюдения и идентификаторы доступны в details; Compact/Expanded и RU/EN сохраняются.

## Breakpoint, свежесть и лимиты

Для уже найденного дефекта можно запросить диагностический `responsive.breakpoint={minWidth:320,maxWidth:430,attempts:4}`. Сначала проверяются границы, затем середина соседней пары с разными результатами. Всего 2–5 попыток, остановка при диапазоне ≤16 px, отсутствии контраста или неоднозначном результате. Это наблюдаемый pass/fail диапазон, а не угаданный CSS breakpoint. Пробы не меняют и не подтверждают acceptance criteria.

Каждый сценарий хранит ревизии загруженных исходников. Повтор неизменённого responsive checkpoint переиспользует evidence и не создаёт новую verification record. Правка независимой статической страницы не обесценивает проверку другого маршрута; изменение загруженной зависимости требует новой проверки. Для dev server без прямого source mapping responsive-кеш отключён и применяется более консервативная ревизия проекта. Внешние runtime-изменения, не наблюдаемые браузером/сценарием, не гарантированно обнаруживаются кешем: задавайте явные state-preconditions и сценарии.

Общий QA anti-loop остаётся активен. Изменение описания, имени сценария или перезапуск страницы не создаёт новый прогресс. Лимиты отдельной операции сохраняются: 6 сценариев, 5 viewport, до 8 steps в сценарии, timeout 500–15000 ms, общий deadline runner 30 s и внешний envelope 90 s. Это не lifetime-бюджет полезных проверок.

Эмуляция размеров desktop Chromium не подтверждает работу iOS Safari, Android Chrome, touch, виртуальной клавиатуры или реального мобильного GPU. Изолированная Page не воспроизводит приватную пользовательскую сессию. Подтверждение качества ограничено конкретными проверенными assertions, маршрутом, размерами и ревизиями.
