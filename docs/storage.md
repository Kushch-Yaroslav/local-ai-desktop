# Desktop storage and session modes

Local AI Desktop reads `${XDG_CONFIG_HOME:-~/.config}/local-ai-desktop-storage.json` before opening Electron or Goose state. This small bootstrap file must stay on an always-available filesystem. `LOCAL_AI_DESKTOP_STORAGE_CONFIG` can select another bootstrap file. An explicitly selected missing file is an error.

The version-1 JSON configuration contains `dataRoot`, `bulkRoot`, and `volumes` (each with an absolute `mountpoint` and filesystem `uuid`). Both roots must already contain `.local-ai-desktop-storage`. Linux mount identity, initialization markers and write access are validated before the backend starts. An unavailable/wrong disk blocks startup with a bilingual error; mount it and launch again. There is no fallback to a new empty profile.

- `dataRoot/electron`: profiles, settings, context overrides and Discovery registry.
- `dataRoot/goose-backend`: Goose configuration, sessions, messages and state.
- `bulkRoot/cache`: relocatable Electron and Hermit caches.
- `bulkRoot/logs`: Electron, Goose request and llama-server diagnostics.
- `bulkRoot/backups` and `bulkRoot/artifacts`: migration archives and local packages.

Sensitive state should use a filesystem with established SQLite/locking/crash-recovery behavior. Bulk paths may use a separately tested NTFS volume. The migration tool installs compatibility links for the former paths and links selected bulk directories into the state tree. Global XDG variables are not changed. `LOCAL_AI_DESKTOP_DATA_DIR` also supports an existing initialized absolute root when no bootstrap configuration is present; it never initializes an empty profile.

`scripts/storage/migrate.py` consumes a private plan (`moves`, `bulkMoves`, `configuration`, `configFile`, `backup`) and writes a private receipt. Close Electron and Goose before running it. It archives all originals, checks file contents and SQLite integrity/counts, verifies copies, and retains originals as `.migration-old` until application verification. Existing destinations must match verified originals before an interrupted migration can resume.

```bash
python3 scripts/storage/migrate.py --plan PLAN.json --receipt RECEIPT.json
python3 scripts/storage/migrate.py --resume RECEIPT.json
# Only after startup, history and profile validation:
python3 scripts/storage/migrate.py --finalize RECEIPT.json
# Close the app first. Restores current data, including messages added after migration:
python3 scripts/storage/migrate.py --rollback RECEIPT.json
```

Rollback preserves original package/user symlinks and materializes only bulk links created by the migration. Relocated copies and the complete archive remain available. Mounts are checked before migration, resume, cleanup and rollback; the tool does not mount or format disks. SQLite shared-memory indexes may be regenerated by SQLite verification; durable database and WAL bytes must match the archive before original-copy cleanup.

Request diagnostics are bounded to 8 MiB per request (plus a truncation marker), ten completed rotated files, a 128 MiB aggregate retention budget, and seven days. Locked active logs are not pruned. Diagnostic write failures warn and stop that log rather than abort inference. Existing logs are archived by migration before normal retention applies. llama-server output is capped at 16 MiB per launch with one rotated prior file; Electron main logs rotate at 4 MiB.

Session mode belongs to each persisted Goose session. The new-chat selector waits for the actual configured default, and an explicit draft selection is acknowledged through ACP before the first prompt. Model capability updates do not overwrite an established mode; stale session-load responses cannot overwrite a newer selection. Chat Only omits all tool schemas at inference preparation while retaining runtime execution safeguards.

## Application Storage settings (Linux)

Open **Settings → App → Application Storage** (**Настройки → Приложение → Хранилище приложения**).
The checkbox and native folder picker edit a draft. Only **Apply location** followed by **Move and restart** changes storage. Reopening settings reads the applied bootstrap; existing version-1 configurations, including separate POSIX/NTFS volumes, remain custom configurations without an automatic transfer.

A new installation uses XDG data for Electron/Goose state, XDG config for Goose configuration, XDG cache for disposable caches, and XDG state for logs. A full custom POSIX folder contains `data/`, `config/`, `cache/`, `logs/`, `artifacts/` and `backups/`. Model weights are not copied; GGUF paths in profiles are preserved. Runtime temporary files stay on the compatible state volume under `dataRoot/runtime/tmp`; this also keeps Unix sockets off an incompatible bulk filesystem. The maintenance process uses a separate temporary profile in the OS runtime directory.

Preflight checks disk identity, write access, atomic rename, available capacity, permissions, links, Unix sockets, SQLite WAL and competing SQLite writers. A short successful probe cannot establish NTFS/exFAT power-loss safety: these filesystems receive bulk categories while durable state and configuration stay on a known compatible filesystem. The UI shows every effective category and explains the split. Network/unidentified mounts are not accepted for durable state.

The original Electron process and every owned backend stop before copying. A separate Electron maintenance process waits for the original PID **and process start identity** to disappear. Chromium can hold SQLite locks even after closing windows, so destroying a window alone is insufficient. Other instances are blocked by a bounded maintenance request in the bootstrap directory. A progress window remains visible while the copy is made.

Files are copied to transaction-owned sibling staging directories, regular files are checked with SHA256, and SQLite integrity is checked without recreating databases. Source data remains intact. Existing destinations are accepted only when they belong to this installation or are a recorded previous source; in-place replacements retain the preceding directory. A full manifest is stored in target `backups/storage-transfer-<id>.json`; the small, atomic control journal is `${XDG_CONFIG_HOME:-~/.config}/local-ai-desktop-storage-transfer.json`. Bootstrap updates are atomic and synced. No global XDG variables, partitions, mounts, models or system runtimes are changed.

After a crash before commit, startup restores the previous configuration/directories. After commit, checksum/database verification runs **before Chromium opens the transferred profile**. The copy is confirmed only after Goose starts and passes its health check. An unavailable volume or failed verification blocks backend startup, with a bilingual error and a recovery action for an unverified transfer. No empty Goose profile is substituted. Mount the disk and launch again to retry.

After verification, settings offer **Return to previous storage** and optional cleanup with a separate native confirmation. Rollback performs a fresh verified transfer of the **current** state, retaining messages created since migration. Cleanup removes only verified, transaction-owned copies that have not changed and are not in use. Historical pre-GUI sources, archives, the Python migration receipt and its rollback script are retained. Compatibility links keep known previous paths resolving after owned-copy cleanup. Returning to default copies current history instead of reopening an older default database.

NTFS bulk copies may not preserve POSIX permission bits; sensitive state remains on POSIX. The GUI migration engine is currently Linux-specific; other platforms report this limitation rather than claiming a safe transfer.
