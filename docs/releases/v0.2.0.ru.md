## Основные улучшения

### Надёжность Agent V2

Продуктивная работа больше не завершается только из-за прежнего фиксированного предела рабочих ходов. Отмена, тайм-ауты инструментов, verification review и восстановление циклов остаются ограниченными. Task Memory и ссылки на наблюдения сохраняют полезные выводы при компактизации. Диагностика повторов стала точнее: несовпадение patch/context требует перечитать файл и исправить аргументы, stale evidence — выполнить новые проверки, а не повторять тот же verify.

Launcher замечает неожиданный выход сервера модели и убирает устаревший ready. Повтор отказанного соединения ограничен, учитывает отмену и происходит только до отправки байтов запроса; частично отправленный инференс не воспроизводится. Состояние задачи сохраняется. Заменённый работающий Rust executable требует перезапуска вместо молчаливого выбора другого binary.

### Два режима и обязательная защита терминала

В UI доступны **Запрашивать подтверждение** и **Абсолютный автопилот**. Реальный broker Rust → Electron обрабатывает разовое разрешение, ограниченные grants запуска, отказ, timeout, отмену и отзыв. Legacy-режимы нормализуются; управление доверенными папками убрано. Автопилот выполняет разрешённые действия в установленном scope, включая локальный Python, без повторных вопросов. Обязательные запреты/внешние операции объясняются отказом, доступ к хосту не расширяется.

Терминал использует обязательные Bubblewrap namespaces, сброс capabilities, NoNewPrivs и seccomp. Проверенная Ubuntu-конфигурация использует отдельный non-setuid helper и enforcing stacked AppArmor, без системного attachment к `/usr/bin/bwrap`. Минимальные allowlists окружения исключают унаследованные loader hooks из Rust/Bubblewrap setup; окружение payload передаётся отдельно. Прямой exec helper из child запрещён. Ошибка старта изоляции закрывает исполнение.

Реестр runtime отслеживает PID/start time, executable, роль, родителей/группу/session, endpoint и lifecycle. Namespaces/ядро защищают процессы хоста независимо от классификатора команд. Managed tasks имеют собственные handles start/status/stop; порт и произвольный host PID не дают права очистки. Штатные Stop Model/Restart/Quit остаются отдельными. Это не неограниченный доступ и не изоляция конфиденциальности; ограничения приведены ниже.

### Независимые задачи и неизменяемая история

Стабильный `logicalTaskId` отличается от conversation, message, generation, analysis run и terminal task handles. План, результаты, Task Memory, проверки и checkpoints принадлежат задаче и сохраняются в SQLite. Независимые запросы не наследуют чужие результаты. Явное продолжение и Regenerate сохраняют принадлежность с отдельными попытками. Selector недавних задач у ввода показывает New task/Continue task и проект.

Активная панель остаётся у ввода только во время исполнения. Завершённые/приостановленные/неудачные попытки сохраняют сворачиваемые снимки рядом с ответами; последующие попытки не переписывают их. Явное продолжение восстанавливает корректный saved workspace без выбранного UI-проекта, не доверяя модельным путям. Legacy-планы беседы сохраняются отдельно; отсутствующие границы задач/evidence не выдумываются.

### Проверка по реальным доказательствам

Checks должны соответствовать задаче, цели/scope, виду проверки и текущим ревизиям. Тест A не доказывает неизменность B; integrity остаётся unverified без доверенного предыдущего baseline. Стандартные direct Python unittest drivers теперь распознаются по scoped-структуре исходника и фактическому непустому test output; раньше успешный скрипт мог считаться только runtime execution. Явные scoped `cd` checks распознаются и при исходном cwd другой задачи.

Идентичные file-tool записи и no-op patches сохраняют файлы/evidence. Узкие literal terminal writes сравнивают наблюдаемые байты до/после, избегая ненужной инвалидации; произвольные mutating scripts остаются консервативными. Реальные изменения по-прежнему инвалидируют проверки. Счётчики различают implemented/verified и точно отображают соответствующий неизменяемый снимок.

### Двухэтапное восстановление циклов

Stage A даёт конкретное указание о повторяемом действии и следующем шаге задачи. При возврате того же цикла без прогресса Stage B сразу пробует selective cleanup, не ожидая ещё одно полное окно повторов. Из следующего запроса модели исключаются только полные доказуемые циклы metadata, включая поддерживаемые `view`/`implemented`. Полезный контекст, пары tool call/result, Task Memory, evidence и вся постоянная история сохраняются.

Неясная граница приводит к безопасной паузе. Число cleanup ограничено (сейчас две попытки); только значимый прогресс сбрасывает escalation. Manual Continue снова включает детектор. Recovery actions сериализуются и подтверждают обработку на границе runtime; timeline показывает предупреждения, попытки, исключения и исходы с раскрываемой диагностикой.

### Конфигурации контекста и UI

Сохранённые FP16/Q8 переживают смену чата и загружаются явно без обязательного discovery. Requested/effective различаются; ошибка сохраняет запрос и сообщает причину backend. GPU-fit разделён по модели/KV/runtime/условиям. Обычная активность первого запроса не инвалидирует измерение; реальные изменения условий дают предупреждение, а не молчаливое уменьшение или скрытие вариантов.

Selector содержит FP16/Q8-столбцы с 16K/32K/64K/128K/256K в пределах поддержки, точные найденные размеры, раздельные индикаторы, клавиатуру и scrolling. Справка Maximum Context помещается в окно и содержит только объяснение точности, два найденных максимума, общую текущую VRAM и предел модели/backend. Расчёты discovery и логи сохранены.

## Другие подтверждённые исправления

- Канонический scope, Git metadata и protected paths проверяются файловыми/patch/download путями; атомарная замена и копии поддерживаемых операций, best-effort rollback.
- Публичные HTTP(S)-загрузки с проверкой адресов/redirect, лимитами объёма/времени, отменой, checksum и атомарным размещением; download не является installation/inference verification.
- Кооперативная пауза при ожидающем approval, Stop/restart restoration и очистка собственных процессов; interrupted tools не воспроизводятся незаметно.
- Mermaid сохраняет исходник, применяет узкую детерминированную нормализацию, показывает parser diagnostics и повтор рендера.
- Группировка reasoning, отложенный разбор больших результатов, ограниченные неактивные caches, понятнее ru/en permissions/status; полной виртуализации истории нет.
- Более ясная диагностика compaction, approvals и sandbox startup; ограниченные стадии acceptance и детерминированная очистка fixtures.
- Source startup собирает Rust через dev workflow. Неиспользуемая model-specific утилита исправления пути удалена; источником истины остаются активные настройки.

## Validation

Проверки и происхождение результатов.

### Исправления RC2

- Контекстный выбор различает выбранный запрос и активную конфигурацию runtime; явная загрузка выделена как основное действие. Модель не перезагружается и настройки не понижаются молча.
- Время терминальной команды рассчитано по timestamps её lifecycle и обновляется, пока детали свёрнуты. Завершение, timeout, отмена и ошибка останавливают состояние выполнения.
- Миграция пакета распознаёт только известную старую unmanaged Bubblewrap-копию, сохраняет backup до замены и fail-closed отказывает для неизвестных или изменённых файлов.
- Stdin foreground terminal отделён от control pipe Rust Runtime; EOF, redirection и heredoc проверены в enforcing sandbox упакованного приложения.

RC2 собран из зафиксированного исходного snapshot, идентичность пакета проверена. Ниже отдельно указаны автоматические проверки, enforcing sandbox и приёмка реальной модели. ## Limitations

Известные ограничения.

Debian maintainer hooks устанавливают отдельный helper без setuid и enforcing-профили Agent AppArmor. Членство учётной записи в отдельной группе явно разрешает администратор; см. [настройку Ubuntu](../ru/GETTING_STARTED.md#требования-терминала-agent-на-ubuntu). Изменённые policy, неуправляемые helper или отсутствие enforcing блокируют конфигурацию без ослабления глобальных настроек.

Проверки содержимого пакета RC2, извлечённого приложения, enforcing sandbox и lifecycle пакета в disposable Ubuntu 24.04 прошли. Контейнер подтвердил отказ в небезопасных условиях и upgrade unpack/removal с сохранением fixture data; он не обеспечил успешную privileged AppArmor provisioning или чистую desktop-установку. По сообщению владельца, установленный RC2 прошёл обновление пакета и реальную Qwen Agent-приёмку на Ubuntu разработчика, включая восстановление после паузы и продолжение между чатами; здесь результат не воспроизводился независимо. Чистая Ubuntu установка и широкая совместимость дистрибутивов не проверены. Отдельная независимая проверка GPU-fit discovery/loading на опубликованном пакете не заявляется.

**Границы безопасности:** host files могут быть читаемы через в основном read-only root, network namespace общий, resource exhaustion/TCP control APIs не полностью изолированы. Некоторые dev tools требуют запрещённых syscalls/sockets. Групповой доступ к helper не удостоверяет только Electron; production spawn исключает обычные унаследованные loader hooks, но не защищает произвольный unconfined-код того же пользователя. Ручной ELF loader может исполнять bytes helper под уже ограниченным child label, не возвращая setup-права. Общей гарантии отсутствия sandbox escape/ошибок ядра нет.

**Ограничения работы:** unsupported checks остаются unverified, особенно integrity без исходного доверенного baseline. Сложный shell может потребовать более простой проверки. Модели всё ещё могут выдумывать evidence IDs и повторять metadata; bounded recovery не гарантирует успех. Compaction с потерями. Legacy-планы нельзя ретроспективно разделить на immutable per-task history. Не заявляются auto backup pruning/общий Undo, полная виртуализация, менеджер gated credentials, OCR и cross-task experience.
